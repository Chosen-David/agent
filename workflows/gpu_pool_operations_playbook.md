# 多机多卡 GPU 资源池的执行与运维层 playbook

适用：多台授权机器的异构 GPU 池（无 Slurm/Ray 等调度后端、SSH 直连 + 脚本派单 + 文件回传的裸环境）上，长期运行大规模评测/扫描/消融任务链时的**执行与运维规程**。

与既有文档的关系：本文是**执行/运维层补集**，不是规划层替代——[单卡独立任务扫描编排](single_gpu_sweep_workflow.md) 解决「分数槽怎么打包、claim 队列怎么原子」；[多机多卡编排](cluster_orchestration_workflow.md) 解决「gang job 波次怎么放置」；两者给出的是**建议（advisory）**。本文回答的是建议落地之后的问题：机器怎么接入、单怎么派、结果怎么回传、口径怎么对齐、长尾怎么治、最后怎么收口。素材全部来自一个真实四机池（本地 2 卡 + 两台 8 卡 H20 机 + 一台 2 卡机，共 20+ 卡）一轮 33 格 × 多臂长文本基准评测任务链的事故与修复；机器身份（IP/主机名/凭据）一律不入库，下文以机器 A/B/C 指代。文中数字为该池单轮任务链的实测观测，仅作量级参考，不外推。

## 0. 池的实况与第一原则

| 机器 | 卡数 | 与本地差异点 |
|---|---|---|
| 本地 | 2 | 代码库、git、收口与打分都在这里 |
| 机器 A / B（8 卡） | 各 8 | 无本地代码库可达（远程内网 git 与本机不同源），**文件回传是唯一数据通道**；模型路径与本地不同 |
| 机器 C（2 卡） | 2 | SSH 走非标端口 + 密码方案；rsync 须用自带包装脚本，**不能**用标准 `rsync -e` 写法 |

第一原则：**每台机器是一个独立环境，不是本地的镜像**。模型路径、数据路径、rsync 通道、端口、认证方式逐机不同；任何「在本地成立」的路径/命令假设，在远程机上都须逐机验证后才能派单。

## 1. 接入规程：拿到 SSH 只是第一步

**事故实录**：派单脚本里 `MODEL=` 用了远程机的模型路径派本地 GPU——本地真实模型在共享挂载的另一路径，`HFValidationError` 25 秒内两个任务全挂，但脚本的 DONE 标记照打，GPU 空转 42 分钟才在人工巡查时发现。

**根因**：① 派单模板按某一台机器的环境写死，跨机复用未改路径；② 任务包装脚本的 DONE 判定在参数解析/加载失败时仍然落盘——「脚本跑完了」被误当「任务完成了」。

**规程（接入 checklist，逐机过一遍，缺一不派单）**：

1. `nvidia-smi` 探卡：卡数、型号、显存实额；同时确认没有别人的在飞作业（快照不是租约，沿用 [单卡扫描编排](single_gpu_sweep_workflow.md) 的纪律）。
2. 环境三元组校验：CUDA 版本、PyTorch 可导入、GPU 可见——一条 `python -c` 冒烟命令解决，不裸信登录成功。
3. **模型路径逐机核实**：`ls` 到权重文件级 + md5 抽验；本地的共享挂载（NFS 类）在远程机可能有页锁问题，**权重拷到远程机本地 nvme** 是根治手段（拷贝逐文件 md5 全对后才切）。
4. 数据集推送：rsync 前**先远程 `mkdir -p` 目标目录**（`--rsync-path` 默认不建目录，接收端报 No such file）；推送后 md5/字节数双端核对。
5. 回传通道验证：rsync 双端可能都没装（内网 yum 镜像 rpm 下载后解包到 `~/.local/bin` 即可用）；每台机的通道脚本**各不相同**（机器 C 须走自带 sshpass 包装脚本），逐机跑一次小文件回传实测。
6. 认证细节：sshpass 读密码**必须带 `-e`**（走 `SSHPASS` 环境变量；不带则不读取，表现为 `Permission denied` exit 5，易误判为密码错）；公钥可能被容器化 sshd 拒绝（`AuthorizedKeysFile` 指向自定义文件），密码方案是兜底而非异常。
7. 首次派单一律 SMOKE：小样本数（如 n=8）实测 wall time 与产出 schema，再放全量。

## 2. 拉回循环：目标目录是易腐状态

**事故实录**：某机的 20min 周期 rsync 拉回循环，在实验代际切换后仍指向海选时代的旧目录——新时代（目录结构变更后）的全部产出从未回传本地，直到收口前本地「缺格」盘点才暴露；另一台机同款问题，部分格子的产出靠手动补拉才入账。

**根因**：① 拉回循环脚本的目标路径是硬编码常量，实验目录结构变更时没有显式更新它；② 循环脚本没有可查询的「最近成功」记录，静默空转与正常工作不可区分；③ 远程机无代码库/agent 通道，**文件回传是唯一数据通道**，循环失效即数据不可达，且无任何报错。

**规程**：

1. 拉回循环脚本必须落「最近一次成功 rsync 的时间戳 + 传输文件数」日志，监督轮查日志不查进程存活（进程活着 ≠ 在拉对的东西）。
2. **实验代际切换（输出目录结构变更）时，显式更新所有机的循环目标路径，并手动补拉一次**作为切换验收。
3. 周期自动循环与手动 rsync 的分工要写明：循环目录若**不覆盖**正式结果目录，正式目录的回传必须在监督轮固定动作里手动拉。
4. **本地状态 = 各机产出的并集**；缺口盘点一律以本地并集为准，不能信任何单机视角（单机看到的「已完成」可能是未回传的）。

## 3. best-file 口径 vs 累计行数口径：执行层与验收层不一致会拒收

**事故实录**：执行层的 SKIP 幂等按**累计行数**判定（同一格所有分片 `cat` 起来 `wc -l ≥ 目标` 即跳过），正式收口仲裁按 **best-file**（同一格多个文件取最大单文件行数）。实锤两格：某格累计 104（=13+91 两个分片）但 best=91；另一格累计 112 但 best=64——远程链按累计口径 SKIP 跳过不补跑，正式收口被 min-samples 门禁拒收，险些烧掉约 8 GPU·h 重跑。

**根因**：两套口径分属两层——执行层需要「别重复烧卡」所以按累计宽进；验收层需要「单文件完整」所以按 best-file 严出。层间没有对齐检查，宽进口径的「已完成」在严出口径下不成立。

**规程**：

1. **派单前的缺口盘点必须按 best-file 口径**：每格取分片中最大单文件行数与目标比较；`head -1` 看单文件行数同样会误判（分片可能有多份）。
2. SKIP 幂等口径与收口仲裁口径**不一致是已知事实**：把「补齐 best-file 缺格」明确列为派单前置检查，而不是依赖远程链的 SKIP 语义替你兜底。
3. 旧分片文件只读保留、新补跑文件用新时间戳落盘，收口走 `--merge-best` 式显式合并（行数最多者胜，幂等）；不要原地改写历史分片。
4. 冒烟残留（小样本试跑的短分片）会混进正式目录，收口合并时按同一 best-file 规则自然排除，但盘点时要知道它们存在。

## 4. 派单纪律：每一条都是实锤事故

| # | 事故实录 | 根因 | 规程 |
|---|---|---|---|
| D1 | 派单后只查 pid 存在就认为在跑；实际任务参数解析失败，DONE 标记照打，卡空转 42 分钟 | DONE 判定不区分「退出码 0」与「解析失败秒退」；pid 存在只证明包装脚活着 | **派单验证双确认**：log tail（看到任务真正起跑的日志行）+ `nvidia-smi` 显存/利用率双指标确认；只看 pid 不算验证 |
| D2 | 派单写了任务名缩写（如 `fwe mv` 中的 `mv`），argparse choices 秒拒，任务从未被认领且无人报错 | 派单者凭记忆写缩写，argparse 拒收不产生 DONE 也不产生告警，静默失败 | **任务名必须用 argparse choices 全名**；派单前对着脚本 choices 列表核对一遍 |
| D3 | 派单脚本签名是 `<GPU> <ARM> <LEN> "<EXTRA>" "<TASKS>"`，EXTRA/TASKS 未整体引号导致散参错位成别的参数，进程秒退 | bash 散参被 argparse 逐个吃掉，位置参数整体错位 | EXTRA/TASKS 这类含空格的参数**必须整体引号**；派单后按 D1 双确认兜底 |
| D4 | 同名任务在 64K 与 128K 变体脚本里各跑一份，被误判为重复撞车 | 同一脚本家族有按序列长度分的变体（`*_ruler64_*` vs `*_ruler128_*`/`*_long_*`），只看任务名不看脚本名会误判 | **判撞车/判重复必须看父链脚本名**（ps 查进程的完整命令行），同名任务在不同长度脚本里各跑一份不是重复 |
| D5 | 基线臂（fullkv）用了方法臂脚本，脚本内 `--method tli` 硬编码，基线跑成了方法臂 | 脚本按方法臂写死，基线复用时未覆盖 | 基线臂须 argparse **后位覆盖** `--method none`（后位参数胜出）；派单后打分前抽查产物文件名里的 method 字段 |
| D6 | 巡查看到某卡瞬时 0% util，误判进程挂了 | GPU 利用率采样窗口内恰逢 CPU 侧阶段（预处理/落盘），瞬时 0% 是采样假象 | 判定挂死前先 `ps` 核实进程 CPU 时间在涨；连续多个采样点 + log 停更才判死 |
| D7 | 想中途停链，直接 kill 整个进程组，把正在写的结果文件打断 | 包装 bash 与 python 计算进程是父子两层 | **杀链纪律：只杀 bash 父进程**，在跑的 python 成孤儿后自然跑完不损数据；杀前确认无共享 FS 写锁 |
| D8 | 远程推送脚本 `cat > file && chmod && nohup ... &` 一条链执行，落地文件 0 字节 | 行尾 `&` 把整链后台化，`cat` 抢不到 stdin | **推送与启动分两次 SSH 调用**；推送后 md5/字节校验再启动 |
| D9 | 想给运行中的链换模型路径，原地 `sed` 脚本 | bash 边执行边读脚本，原位改字节偏移可能让解释器读错位崩掉 | **运行中的脚本不能原地改**：改动走环境变量注入，或等重挂窗口统一替换；必要时新脚本新文件名 |
| D10 | 推代码给远程机用 `scp` 工作树当前版本，结果推过去的是 agent 正在改的半成品 | 本地工作树被并行 agent 边写边推，快照不一致 | 推远程一律用 `git show HEAD:<path>` 取已提交版本；脚本推送做 md5 双端校验 |

## 5. 长尾治理：倒序包抄（reverse encirclement)

**场景实录**：某 GPU 的串行任务队列深达五级（`mq→mv→cwe→fwe→vt`），其中 `fwe` 单格约 12h，全局限界被这条链的尾部拖住；此时另一台机出现空闲卡。派空闲卡**从队列尾部倒序**跑 `[cwe,fwe]`（与原链相向推进），全局限界从约 12h 压到约 6h。

**根因（为什么可行）**：串行链的 makespan 由尾部决定，而尾部任务与头部任务互相独立——补位卡不必从队列头重跑，直接攻最深的尾部格即可。约束是防撞车：

| 前提 | 作用 |
|---|---|
| 任务幂等 + SKIP 兜底 | 两链同格时先完成者生效、后到自动跳过，冗余执行零风险（同 [单卡扫描编排](single_gpu_sweep_workflow.md) T3 backup tasks 的投机执行语义） |
| 缺格按 best-file 盘点（§3） | 只包抄真正会拖限界的格，不浪费卡 |
| 派单前 ps 全量归属核对 | 三机所有在飞进程的完整命令行核对一遍，确认哪些格已被哪条链认领；**只包抄无人认领的格或认领链尾部最深的格**，并错开与在飞链的撞车窗口 |

**规程**：发现空闲卡 → ps 全量归属核对 → best-file 缺口盘点 → 从最深尾部倒序认领 → D1 双确认起跑。包抄链与原链对同一格的冗余由 SKIP 幂等仲裁，不做人工撤销。

## 6. 收口纪律：闭环是三个独立动作，不是「文件都在了」

1. **正式入口收口**：打分必须走正式入口（冻结 manifest + 评分门禁 + 身份闭包 + 原子发布），不是「产出文件都在目录里就算完成」；min-samples、行数、schema、跨臂身份逐项过门禁，fail-closed。
2. **「生成完」≠「证据闭环」，两件事分开列**：任务链清单里「全部格已产出」与「全部数字已 commit 可验、可入下游（论文/报告）」是两个验收态；后者还差收口打分 + 收口产物入库。汇报时分开说，不合并。
3. **数字落 commit**：收口产物（summary/receipt/结果 JSON）与代码同 commit push，任何人可从 commit SHA 复算；不落 commit 的数字只算中间态。
4. **多 worker 并发写共享 git 索引**：多个 CPU agent 并发在同一仓库 commit 实测撞 `index.lock`。规程：**CPU 侧子任务用 `git worktree add` 隔离工作区 + 独立输出目录，只由主协调者串行汇入**；GPU 远程机不 git（见 §2，文件回传是唯一通道），不存在此问题。
