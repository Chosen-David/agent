# 长上下文、advice 生命周期与多 AI 协作设计

日期：2026-10-09。任务：CTX-20261009-01。目标是减少重复输入，同时保留正确决策所需的前提、反例、版本和证据。本文件区分已经实现的小修复与后续架构建议；数据库、自动整理和真实模型预算管理尚未部署。

## 1. 当前判断与可核查问题

长上下文的风险成立，但文件多不等于模型已经加载全部文件。问题在入口怎样选择和反复传递内容。此次只检查 agent checkout；本机没有 SGLang checkout，未核实其 advice 数量、活动引用或远端运行状态，也未修改 SGLang。

初始清点：agent 的 advice 有7文件、43,818字节；193份任务详情约364KB；results 有2220文件、约33MB。这是文件系统统计，既不是 token 数，也不是当前模型输入。两个主调度源码分别约30KB和32KB；便携入口为了可独立分发有重复规范，部署者同时加载多个入口会有额外成本，不能根据文件体积推断宿主实际加载行为。

已有机制可复用：KnowledgeStore 按需检索及强前置闭包；MemoryLedger 的不可变 ID、来源与纠错失效；Mailbox 的定向投递、幂等事件、消息字节预算；basis_context 的消费者选择、实际 tokenizer 可选硬限及超预算拒绝；独立计划与独立结果审核。现有 SQLite 不是完整多机共享内存系统，也不自动运行 LLM。

发现的具体问题：

1. `task_document_refs` 原来深拷贝整个项目快照，再筛任务详情，却保留全部 advice inventory。T个任务、A个建议会重复传递T×A个路径/hash记录，虽然正文没有被复制。
2. `validate_advice_assessments` 要求覆盖全局快照中的所有建议。缺少持久、带适用范围的处理记录时，历史意见容易在新计划中反复评估。当前还包括 advice README 等目录说明。
3. 历史任务详情存在格式缺口，严格项目快照会阻断。不能让错误格式导致“只有巨型聊天记录还能继续”的隐式后备路线。
4. `write_task_progress` 检查稳定 Plan 哈希，但它不是多作者对 Progress 的比较并交换锁。两名不遵守单作者约定的主 AI 仍可能覆盖彼此的进度；原子替换文件不等于避免丢失更新。这是越过现有单作者契约的风险，不是已复现的受支持并发路径 bug。

## 2. 本轮已实施的边界

每个节点的 `document_refs.advice` 现在只携带其 adopt/adapt 来源，与该节点 `adopted_advice` 一致；过滤发生在深拷贝之前。全部指南、指南评估、当前稳定任务依赖和未知扩展字段仍保留。全局快照仍携带完整建议清单，全局评估覆盖规则不变。

这是引用去重，既没有摘要意见，也没有自动认定意见有效，更没有解决全局重复评估。旧冻结计划不自动改写；完整契约验证不接受旧的全量节点形状，须创建新版本并重新审核。源码更新不代表正在运行的旧宿主或已安装技能自动更新。

任务格式修复及实测范围见 [本轮报告](../agent_doc/results/advice-context-20261009/report_by_gpt.md)。历史原文、失败尝试与独立审核均保留。人工 guide 不写入。

## 3. 建议采用的分层

| 层 | 内容与权威 | 存储和读法 |
|---|---|---|
| 当前约束 | 当前用户、宿主权限、核实来源的人类指南、当前任务及未解冲突 | 每次检查版本；必要约束不能因省 token 被删除 |
| 活跃决策 | 已采纳意见、当前方法、拒用原因、关键未决项、下一动作 | TASK详情＋有来源的项目记忆；短摘要导航，按需回查 |
| 通用知识 | 经核验、带前提的定理/方法/工程结论 | 现有 knowledge ID/version/hash；只加载少量条目及前置 |
| 原始证据 | 各 AI 反馈、会议原文、代码/测试、失败结果与验收回执 | advice/results原路径与固定hash；完整保留，不常驻提示 |
| 派生索引 | 文件分类、检索字段、处理状态、依赖反向索引 | 可重建 SQLite；无权自行授权、采纳或覆盖源文件 |

“融合进知识库”应发生在可复用主张层，而不是把一整场会议改写成一个大知识条目。SGLang 某次 kernel bug、某模型逐层参数、某轮显卡占用是有版本的项目事实；只有可推广且核验过的规则才考虑公共知识入口。项目私有内容不能自动提交公共 agent 仓库。

## 4. advice 的增量生命周期：推荐下一阶段

建议增加独立于原文的处理记录，不移动源文件来表达状态。以下字段是设计草案，不是已经可调用的 API：

```json
{
  "advice_id": "project-topic-author-sequence",
  "source": {"path": "agent_doc/advice/original.md", "sha256": "..."},
  "task_refs": ["TASK-ID"],
  "claims": ["claim-id"],
  "disposition": "adopt|adapt|reject|defer",
  "reason": "evidence and exact scope",
  "input_versions": {"task_plan": "...", "guides": "...", "code": "..."},
  "evidence_refs": [],
  "supersedes": [],
  "conflicts_with": [],
  "reviewer": "actual invocation reference",
  "resume_condition": "explicit condition if deferred"
}
```

生命周期不能压成一个混合 status：处理决定、内容新鲜度、检索可见性各自记录。例如 defer 可以是新鲜但缺 GPU，也可以因代码更新而 stale；archived 只表示默认检索视图不显示，不表示已拒绝、已验证或可以删除。

增量流程：扫描路径/hash得到新增或变更集合 → 找当前任务及显式依赖候选 → 复用同一来源hash、适用范围和前提版本的处理记录 → 对未知范围、冲突、撤回、失效证据重新审查 → 主作者提交新的处理记录与任务改动 → 下一检查点重新核验消费者。

缓存键至少绑定来源hash、任务稳定Plan、指南版本、处理范围及真正影响结论的代码/配置/证据版本。对任务A的reject不能自动扩成对任务B的reject；改过意见正文不能沿用旧采纳；同名文件不能作为相同来源。语义相似只提示去重候选，不能替代等价性和适用性检查。

需要同时维护两种覆盖：整个清单的“已发现/未处理”覆盖，以及当前任务的“已审查/适用/不适用”覆盖。当前严格全覆盖门禁在新记录接口与可信消费者接入前保持原状。不能先删掉覆盖要求，再声称增量治理完成。

## 5. 整理、归档与清理

优先逻辑归档，不优先物理删除。默认视图只显示当前活跃意见、与本任务相关的未决反例、近期更正以及必须恢复的阻塞；完整原文仍按 ID/path/hash 可访问。

整理触发优先按任务关闭、来源变化、积压量和上下文预算，而不是固定时间反复开多 AI 会议。具体阈值由真实负载测量确定，本轮不新增定时器。一次整理限制处理文件数/字节/模型调用和总预算；连续无新增材料就退出。

归档前查反向依赖：活动任务、交接、知识条目、独立回执和论文证据仍引用的文件不得移动或删除。即使已合并，仍保留原始引用和 supersedes 关系。生成缓存、可重建索引和已结算的自有临时产物才可能清理；源建议、失败日志和验收证据不因“看起来没用”自动删除。搬家须显式映射并验证全部消费者，不能用断链来省上下文。

避免所有 AI 都改一份会议纪要：作者各写自己的不可变意见/patch，主 AI 维护短的决策记录。开会时传“本轮新增观点＋反对意见＋证据引用”，不给每名参与者广播全部历次会议。保留不同意见的可追溯条目，不以赞同票数当证据。

## 6. 数据库与临时数据库的取舍

| 方案 | 适用 | 限制 |
|---|---|---|
| Git文件＋JSON处理记录＋本地SQLite索引 | 当前推荐起点；可审计、易恢复、无需模型服务 | 索引更新必须检查来源hash；JSON多写者仍需串行提交 |
| 每run临时SQLite | 有界候选集合、检索和去重计算 | 重启后可重建；不能保存唯一一份长期決策/授权 |
| 单主机持久事务账本 | 需要本机多进程协调、幂等与版本提交 | 不能凭 owner 字段证明实际作者；事务不验证语义 |
| 跨机协调服务/事务数据库 | 多机需要租约、唯一提交者、访问控制与故障恢复时再评估 | 部署、运维、认证、备份、网络分区处理有成本；本轮未实现 |

向量索引可辅助相似检索，但不应成为第一项必需依赖；准确ID、task_refs、hash、状态、词法检索和反向依赖先解决可核查问题。索引损坏时可以重建；缺失索引不能被解释为不存在原始证据。

SQLite WAL 要求共享数据库的进程在同一主机，不支持跨机器通过网络文件系统共享其 WAL。[SQLite官方说明](https://sqlite.org/wal.html)。当前 ledger 使用事务，但不能据此声称已具有跨机一致性；推荐每机本地缓存，只有协调主机/服务提交共享决策，远端传版本化事件与文件hash。

## 7. 多 Agent、多主 AI 的一致性与恢复

每个 project_root/逻辑任务指定唯一 planner/提交者，review-main 只返回意见。不是全系统只能有一个主 AI：不同项目/互不重叠的写入范围可以并行；共享 TASK、已采纳决策和同一产物必须有明确串行提交边界。

后续多主写入接口应采用 expected_revision 比较并交换；确需主控接替时由可信协调器发租约及单调 fencing token。旧主控恢复网络后不能靠旧token继续写。不能把本地lock文件、JSON中的owner或 Git分支名字当成跨机独占证明。无法认证新的owner时停相关提交分支，其他已授权只读/独立任务可以继续。

读者固定一个 revision 快照，返回来源hash、适用范围及结论；写者提交原子的新revision。事件按 event_id 幂等处理，ACK 只是收到/处理，不等于科学验收。更正撤回沿显式依赖图失效相关摘要和结论，保留历史原始观测；遗漏的语义依赖仍需人工/模型审核。

压缩上下文或换模型会话后，清空该消费者“已在当前上下文保有正文”的缓存提示。共享引用命中不代表共享模型KV缓存；历史内容保留在磁盘也不表示当前模型已读。两主 AI 看见相同ID但不同hash时须协调，不用最近时间戳、多数意见或最后写入胜出悄悄解决科学冲突。

## 8. token 预算的数学视角与实现要求

自己的成本推导：若每轮追加h个token，且每轮重新发送整个历史，无缓存折扣时，n轮总历史输入是 nL₀+h·n(n−1)/2，随轮数呈二次增长。它是重复输入量模型，不是所有模型的实际计费或注意力复杂度。若每次只加载有界的核心约束c与必要检索r，总输入可界为 n(c+r)，但前提是依赖与反例能在预算内完整表达；不能通过删除必要信息强行满足这个界。

可把选择表述为依赖约束下的预算问题：必需集合R必须包含，选择X须包含每项的强前置，并满足实际token成本 cost(X)≤B。相关度只作为效用估计，不能替代正确性。依赖闭包和冲突项会改变可行性，不自动满足经典贪心近似定理的前提。

实际宿主每次调用前核对：模型窗口－系统/工具schema－当前用户输入－输出与推理预留－安全余量；还有整轮已花费预算。可选导航先少量取回，再按需读原文。超过硬限则缩小任务或拆分依赖链，不能截断证明、偷偷放宽限额或丢掉反例。

同时记录 input/output/reasoning tokens、缓存输入、工具返回、检索/整理/摘要/审核/重试成本。只报工作 Agent token 会遗漏整理开销。减少峰值上下文也可能增加检索次数，必须比较总成本与正确性。没有匹配目标模型的实际tokenizer/usage时标unknown，字符数绝不除以4冒充token。

## 10. 后续实验与实施顺序

第一步已做：引用去重、格式修复、公开程序拒绝/版本检查及同输入表示体积测量。第二步推荐：在保持严格建议覆盖规则下增加版本化处理记录和只读可重建索引，再接现有主 AI 检查点。第三步再验证消费者的紧凑入口与跨机协调；不一次性替换全部prompt或引入新的权威数据库。

真实模型验证固定同模型/工具权限/任务输入/总体预算，比较：A现有全量治理、B来源检索但每轮重新处理、C带版本处理缓存和生命周期、D进一步增加摘要。任务应含长序列代码修复、分歧意见、错误已采纳观点被更正、无关大量旧文件、指南更新、跨会话恢复与环境漂移。保留未用于开发的题；公开/调试后改标开发题。

主要指标同时看独立验收正确率、错误采纳率、陈旧意见误用、必要反例遗漏、完整证据可取回率、总tokens/费用、P95延迟和返工。不能只优化检索重合度、目录文件数量或短摘要比例。预先约定质量非退化阈值；特定格式失效、权限越界、证据丢失和过期依据漏拒应单独列为阻断项。不同硬件/调用噪声与无法测得指标明确标出。

程序层先测双写冲突、旧revision提交拒绝、租约过期、重复事件、网络分区后旧主恢复、索引重建、来源变化、缓存失效、未决反例预算溢出和检索unknown。应用层测试不能冒充操作系统权限隔离、形式化一致性证明或跨机部署。
