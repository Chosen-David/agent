## Finding and boundary

The two reproduced ACK-first failures are a host ordering/protocol hazard, not evidence that the current Mailbox implementation loses SQLite state or violates its documented per-operation transaction contract. `acknowledge` commits an immutable handling receipt; `inbox` selects only deliveries with a NULL receipt. It deliberately does not inspect whether `needs_revision` has a corresponding request. `test_ack_is_scoped_immutable_and_not_completion` explicitly exercises standalone needs_revision ACK. `publish` independently commits event and all approved deliveries atomically. No present API promises a transaction spanning these two calls.

There is a real workflow enforcement gap: workflow step 5 requires a revision request alongside needs_revision but says neither a precise durable ordering nor how to recover the intermediate states. The demo already uses the safe ordering: persist finding/event, publish E-revision-F1, then ACK the incoming review delivery. Thus the evidence diagnoses a plausible unsafe adapter and insufficiently explicit protocol, not a failing existing demo or established production incident. Normal-inbox polling alone cannot recover the ACK-first state; a host can still reconcile the durable receipt/status and finding records. That reconciliation is not automatic in this module.

The read call chain is trusted host -> independent request/ref validation -> semantic/idempotent action -> separate ACK. `consume_handoff` returns data without ACK; review/question records use host reference checks rather than that handoff-only method. Original reviewer revalidation and scientific finding closure stay outside Mailbox. Adding a transaction would not alter those responsibilities.

## Cheapest maintainable candidate

Prefer an explicit publish-before-ACK protocol using the existing API, with focused adapter recovery tests, before adding runtime machinery. Persist the exact intended event ID/body, original finding and exact two-field receipt; use immutable reference files. On restart, replay the same publication, then the same ACK. Failed publication must leave the incoming receipt unchanged and the incoming delivery pending. A crash after publication should leave a durable downstream request and a pending incoming delivery; retry should deduplicate publication. Neither state constitutes scientific completion.

The intended receipt must be stable across retries, including reason text. Before publication, read the incoming status: an incompatible existing consumed/rejected/needs_revision receipt requires reconciliation, not a blind publish-and-ACK sequence. A status precheck alone is not concurrency protection. The existing single-consumer-per-recipient host constraint is material; absent exclusive ownership, a concurrent conflicting ACK remains a race.

Existing saved event/receipt/finding files can provide recovery intent without a new general journal. Use a small host journal only if the actual adapter cannot reconstruct the exact stable intent from those artifacts or must reconcile ACK-first historical states. An append/durable-write and replay contract, owner, run/version binding, state reconciliation and failure reporting are necessary; merely writing a journal 'before either' does not atomically couple it to Mailbox. Avoid competing task/finding databases. A historical ACK-first receipt has no structured follow-up ID, so reconstruction from free-form reason alone is unreliable; preserve original finding records and ask the accountable host to reconcile ambiguity.

An opt-in combined transaction is a possible stronger local invariant, not yet a necessary remedy. It can commit a validated follow-up event/deliveries plus a compatible incoming receipt together or roll back both. It should reuse publication/receipt validators, retain unchanged legacy ACK behavior, bind follow-up sender to incoming recipient and bind run/task scope, and preserve per-recipient receipts. Exact duplicate event does not necessarily mean all recipients still have pending work: their receipts may already exist. A transaction cannot guarantee external scientific actions exactly once, freeze mutable files, close findings, or protect unmigrated ACK-first callers. Added API/CLI and validator factoring are maintenance costs requiring discriminating benefit evidence.

## Missing discriminating acceptance tests

- Valid publish-first recovery after crash before publish, after successful publish/before ACK, and after ACK; restart with stable original intent and show one event, independent subscriber deliveries and immutable matching receipt. For post-ACK recovery use saved intent/status rather than inbox alone.
- Missing/mutated reference, stale envelope, unapproved route, and exhausted event/message budget before ACK; assert incoming remains pending and no partial new event/delivery. Distinguish validation failure of a new event from duplicate retry failure after reference mutation.
- Pre-existing consumed/rejected/conflicting needs_revision receipts, wrong incoming recipient/run/sequence, and exact matching receipt. Define whether a candidate rejects without new publication, reconciles, or reports a conflict. A precheck-only candidate must state its single-consumer assumption.
- Same event ID with changed content and exact retry at the budget limit. An atomic candidate must reject incompatible incoming ACK without leaving a new outgoing event; matching existing event plus missing/matching incoming receipt must have defined retry semantics.
- Multi-recipient outgoing event with one subscriber already ACKed: retry must not reset that subscriber or collapse others. Check independent incoming delivery receipts as well.
- Host journal control: interruption after durable intent but before publish, after publish but before journal progress, after ACK but before completion marker; stale/corrupt/incomplete intent; missing replay; new-run budget migration. Require explicit unresolved states rather than silently marking success.
- Only if atomic operation is proposed: real separate-process termination before commit/at internal insert boundaries and after commit, plus deterministic raised failure after event insertion but before incoming receipt update. Assert all-or-neither after restart and verify validators/budget/duplicate semantics remain equivalent. A crash before the public call alone does not discriminate atomicity.

## Preregistration issues

**REV-W2-DESIGN-001 — Candidate applicability conflicts with universal legacy-path criterion.** The primary criterion in plan.md says zero stranded requests across the four paths including ACK-first while also preserving the legacy two-field ACK. A publish-first protocol or opt-in transaction cannot satisfy that universal statement for unchanged ACK-first callers. comparison.md acknowledges the problem and recommends binding evaluation to migrated usage, but the original criterion remains textually absolute. Resolve with a versioned clarification before candidate execution: reproduce and retain unsafe legacy controls, evaluate the supported/migrated protocol under identical fault/budget conditions, and state unmigrated callers remain unsafe. This is a reliability/control comparison, not a performance or model-quality improvement. W1's frozen plan/results and original failures remain unchanged; any new acceptance definition applies only to the next experiment after preregistration is frozen.

**REV-W2-DESIGN-002 — Retry visibility does not establish completed recovery.** The baseline's `stranded_repair_request` metric is `(reviewer_pending == 0 and code_pending == 0)`. It captures loss of normal-inbox retry visibility, not eventual repair recovery or actual semantic work loss. Publish-first exhausted budget reports false even though no repair request was published: retained incoming work is the useful outcome, and budget reconciliation/new-run migration is still unresolved. Neither docs nor results should call that a completed repair. Distinguish durable retry opportunity, request persisted, eventual handling and reviewer closure. Retain W1's original metric and observations; preregister completed-recovery predicates for the next experiment rather than applying a new standard retroactively.

baseline_replay.py genuinely uses a child process with os._exit(73) after one committed operation for interruption cases; budget cases execute in the parent and do not resume after budget exhaustion. Publish-first interruption does exercise duplicate publish then ACK on restored Mailbox. ACK-first cases demonstrate stranding but do not attempt status/journal reconciliation. Therefore baseline does not show host-journal ineffectiveness or prove a transaction is uniquely needed. Its runtime digest and fixed evidence are useful; future replay metadata captures executing HEAD rather than automatically remaining the historical baseline. Bind candidate/control code identities explicitly. Existing four cases are disclosed development controls, not heldout crash points; enumerate and freeze additional fault sites before implementation without retrospectively relabeling them heldout.
