# 结论：四倍不成立；无损要先说清保留的是哪种目标采样

按常见的“每生成一个 draft token 花 0.2T”解释，且每个到达深度的条件接受概率都为 90%，这组数给出的模型估计只有 **1.094×**。若 0.2T 指八个 token 整批 draft，估计为 **1.459×**。这两项是条件式计算，不是设备实测。

大模型验证直接 argmax，一般不能保留目标模型的 temperature/top-p 随机采样分布；但如果比较基线本来就是同样的 greedy 策略，并正确核验连续前缀，则可以保持该 greedy 输出。draft 和 target 的采样参数不必相同；关键是目标分布不被换掉，以及校正使用的 q 确实是 draft 实际抽样分布。

## 1. 为什么不能至少快四倍

令目标模型基线单 token 时间为 T。每轮提议 γ=8 个 token，N 是从头连续接受的数量，L=N+1。这里的额外 1 是第一次拒绝后的校正 token，或全部通过后的 bonus token。暂不考虑 EOS/长度截断，并假设相关计算已经包含在给出的验证成本里。标准算法及其理想成本模型见 [Leviathan 等，ICML 2023，§2–3](https://proceedings.mlr.press/v202/leviathan23a/leviathan23a.pdf)。下面保留你给出的 4T 验证成本重新计算。

- 每个 draft token 为 0.2T：轮成本 C=(8×0.2+4)T=5.6T。
- 整批 draft 为 0.2T：轮成本 C=(0.2+4)T=4.2T。
- 若每个“前面都已接受”条件下的当前接受概率都是 0.9，则 E[L]=1+0.9+0.9²+…+0.9⁸=6.12579511。
- 长序列、固定同口径成本下，速度比 S=E[L]T/C，因此分别为 6.12579511/5.6≈1.094，或 /4.2≈1.459。

更直接的反证：一轮至多输出 9 个 token。即使 100% 接受，上述两个成本口径的速度上限也分别只有 9/5.6≈1.607×、9/4.2≈2.143×。单是 4T 验证，即使 draft 免费，也把这种每轮最多 9 token 的方案限制在 2.25×。没有 bonus 时上限还会降低。

不能把“减少大模型调用次数”当作“耗时等比例减少”：你的整批验证不是一次普通单步的成本。严格获益的条件是 E[L]T>C；在每步 draft 的几何假设下，额外开销只要达到约 0.526T，1.094× 的余量就消失了。

## 2. “平均接受率 90%”的分母很重要

一般恒等式是：

E[L]=1+Σ(i=1…8) P(前 i 个都接受)。

推导很短：N=Σ(i=1…8) 1{N≥i}，再取期望。它不需要独立性。只有各到达深度的条件接受概率都为 0.9 时，前 i 个都通过的概率才是 0.9ⁱ。一个混在所有位置、所有输入上的平均数不足以确认这一点。

可核对的相关性反例：把一批的八个“潜在核验结果”预先写成真/假，不表示拒绝后还会提交后续 token。

- 90% 的批次八个全通过，10% 八个全失败：每个位置的边际通过率都是 90%，但 E[L]=0.9×9+0.1×1=8.2。
- 20% 的批次全通过；其余八种情况各占 10%，分别只有第 1、2、…、8 个失败：每个位置的边际通过率仍是 90%，但 E[L]=0.2×9+0.1×(1+2+…+8)=5.4。按 5.6T 成本，速度比为 0.964×，反而更慢。

这两个合成事件分布只用于证明“边际接受率不足以确定前缀收益”，不冒充模型测量。

另一种口径则可以直接用：若你实测的 90% 明确定义为“实际提交的连续 draft token 总数 / 全部提议 token 总数”，并且每轮固定提议 8 个，则平均 N 就是 7.2；在每轮另输出 1 个且不被截断时，平均 L=8.2。这时两种成本下分别约 1.464×、1.952×，仍达不到四倍。不要把这个指标与条件接受率混用。

## 3. argmax 到底保留什么

固定前缀，设目标实际采样分布为 p，draft 实际提议分布为 q；两者都应已经包含各自的 temperature、top-p、归一化及其他 logits 处理。标准随机校正先从 q 提议 X，以 min(1,p(X)/q(X)) 接受；拒绝后从 r(x)=[p(x)−q(x)]₊/Σ[p−q]₊ 抽样。不是拒绝后随意 argmax，也不是直接重抽原始 p。[Chen 等，固定 v1，Algorithm 2 与 Theorem 1](https://arxiv.org/pdf/2302.01318v1)

自己逐项核算：接受并输出 x 的概率质量为 min(p(x),q(x))；拒绝分支补上的质量为 [p(x)−q(x)]₊。相加恰好为 p(x)。这就是所需的分布保持条件。

二 token 小例子，词表为 {A,B}：

- 目标 p=(0.6,0.4)，实际 draft q=(0.9,0.1)。
- 提议 A 时以 0.6/0.9=2/3 接受；提议 B 时必接受。
- 接受分支的质量为 (0.6,0.1)，剩下 0.3 的拒绝质量全部补给 B；最终正好为 (0.6,0.4)。
- 若验证仅保留与目标 argmax 相同的 A，遇到 B 就替换成 A，最终变成 (1,0)。这与 greedy 基线一致，但丢掉了随机基线的 40% B。
- 若仍做概率接受，却拒绝后直接从 p 重抽，结果是 (0.6,0.1)+0.3×(0.6,0.4)=(0.78,0.22)，也错。

top-p 仅作用于 draft 并非天然错误。例如裁剪使 q=(1,0)，目标仍为 p=(0.6,0.4)：A 以 0.6 接受，另外 0.4 经残差输出 B，依然精确。因此不要求 draft 覆盖 target 全部支撑；要求的是用裁剪并重新归一化后的真实 q，而不是裁剪前的概率。若你确实想保留目标 greedy，p 应定义为固定 tie-break 下 argmax 的点质量；draft 可以随机，正确匹配验证最终仍得到 greedy 序列。

## 4. 适用条件与该测什么

正确性先检查：

- p 对应原来要保留的目标策略；温度、top-p、惩罚、终止规则、数值精度的基线定义明确。
- p/q 落在同一 token 空间；不同 tokenizer 必须有正确概率映射，不能直接对齐 token ID。
- q 等于真正生成候选的条件分布；验收随机数正确；只对 q(X)>0 的实际候选取比值；p=q 时不进入零质量残差分支。
- 逐位置概率、attention mask、位置和 KV cache 对应同一前缀；第一次拒绝后丢弃后续草稿。数值稳定性、缓存回滚和 EOS 截断另测。
- 分布相同不意味着相同 seed 逐 token 相同，也不等于不同数值 kernel 必须 bitwise 相同。

性能最小记录：

1. 每轮提议数、连续接受数 N、实际发出数 L、第一次拒绝位置、bonus/EOS 截断；给出 90% 的准确分母，最好直接统计前缀生存概率或各深度条件接受率。
2. 分别测 draft 整批时间、验证时间、校正采样、缓存管理、通信和同步等开销，并测真正的端到端时间；允许重叠的部分以真实时间线为准，避免重复计费。
3. 固定目标模型/权重、dtype/量化、采样参数、输入和输出长度分布、硬件、软件版本、batch/并发与资源预算。预热后正确同步计时，重复测量并报告波动或置信区间。
4. 用总体“实际输出 token 总数 / 总耗时”对照同配置基线，而非平均每轮速度比；单请求 decode 延迟、TTFT/端到端延迟、并发吞吐及尾延迟分别报告。draft 占用的额外设备和显存也要交代。

先用小词表枚举验证采样器分支，再在目标负载上做配对基准。有限样本分布检验可以发现问题，不能替代正确性论证。当前回答只完成有理数小例与条件推导，未运行模型或 GPU，因此不声称获得了任何真实加速。
