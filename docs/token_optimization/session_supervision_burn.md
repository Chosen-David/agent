# 主会话监督循环的 token 消耗瓶颈与治理

来源：sglang/two-level-attention 科研监督主会话 2026-10-10 实测（Claude Code 主
AI + 4 个定时监督器 + 多后台修复 agent 并行的长周期 session）。与
[README](README.md) 覆盖的 Codex 入口/派发层优化互补：本文全部是**主会话运行
期**的消耗，即入口加载完成之后每个监督轮、每次工具调用持续再烧的部分。

## 按量级排序的瓶颈（实测）

### 1. 任务列表全量注入（最大头，占监督轮浪费的绝大部分）

Claude Code 会在**每次工具调用结果后**把任务列表作为 system-reminder 重新注入
主会话上下文，且单次结果里经常出现两份（列表本体 + 任务系统回显）。

实测触发场景：长周期科研监督 session 累积了 78 个任务（其中 ~57 个已完成、
结论早已收割落盘到项目 TASK.md 与记忆），每个任务带完整中文描述。单次注入
~3000-5000 tokens，一个监督轮里注入多次，一个 session 累计烧掉数十万 tokens
——而其中 70%+ 是早已收割完毕的死任务。

治理（已执行，效果实测）：
- **收割即删**：任务完成后立即 `TaskUpdate status=deleted` 永久移除，不要让
  completed 任务留在列表里过夜。收割结论先落盘到项目任务文档再删，不丢信息。
- 删除后从 78 条降到 21 条，注入体积降约 75%。
- 列表里只保留 pending + in_progress；blockedBy 引用已删任务会悬空但无害
  （语义正确：blocker 完成即解除阻塞）。
- 任务描述写短：创建时一句话说清交付物与验收，细节放项目 task_details 文档，
  列表不是详情存储。

### 2. 高频定时监督器叠加

4 个监督器（advice 拉取 30min、GPU 池 30min、任务链 1h、代码审查 2h）在长
session 里意味着每小时 6+ 轮触发，每轮即使无新内容也会走完「查询→汇报」链。

治理：
- **按事件源实际变更频率定周期**：GPT advice 实际 1-2h 才来一次新提交，
  30min 拉取 4 轮里 3 轮是空转 → 放宽到 2h（用户指令后已改）。
- **空轮两行收**：把「无新内容时输出不超过两行、禁止多余动作」写进监督器
  prompt 本身（cron prompt 是每个监督轮的固定加载项，写短省双份）。
- 监督器 prompt 自身也要压缩：协议步骤合并、只留判据与纪律，不重复堆背景。

### 3. MEMORY.md 顶格加载

MEMORY.md 每个新会话/每个子代理启动都全文加载，200 行上限即固定成本。

治理：
- **索引化**：只留结论指针与「哪个文件有细节」，判决细节迁 topic 文件
  （`round3_details.md`、`history_supervision_1009.md`、`e73_e86_history.md`）。
- 接近 200 行就立即迁移，不要等截断警告；重复条目合并（同一事件的多轮监督
  记录合并成一条带时间线）。

### 4. 长文件全文重读

GPT advice 文件 100-200 行、实验报告更长，核验时全文 Read 一遍是常态。

治理：
- 先 Grep 定位（审计文件都有结构化小节），Read 用 offset/limit 只取相关段；
  代码核验只读行号附近 ±30 行，不重读整个文件。
- 互写回应用 Edit 追加到文件末尾，不整文件重写。

### 5. 子代理派发的隐性成本

每个后台 agent 启动都重新加载全局 CLAUDE.md + 项目 CLAUDE.md + MEMORY.md；
若派单 prompt 不自包含，agent 还会花大量工具调用重新探索代码库。

治理：
- **派单 prompt 自包含**：直接给文件路径、行号、方案要点、验收命令、worktree
  路径，让 agent 零探索开工；「先探索再修」的模糊派单烧掉的是双份 token。
- 后台 agent 用 run_in_background 挂着等完成通知，不要轮询 TaskOutput。
- 收割 agent 报告时只读其最终 message + diff，不重放其全部工具输出。

## 通用 trick 清单

1. 收割即删任务（见 #1，本 session 实测最有效单点）。
2. 定时器周期对齐事件源真实频率；空轮两行收。
3. MEMORY.md 索引化 + topic 文件化，触线即迁。
4. Grep 定位 + offset/limit 局部读，替代全文 Read。
5. 派单 prompt 自包含（路径/行号/验收标准），杜绝 agent 重复探索。
6. 回应互写用 Edit append，输出保持短（每轮汇报压缩成判决句 + 证据指针）。
7. 后台任务靠完成通知，不主动轮询。
8. 工具结果里出现的 system-reminder 会随对话重复注入——这不受宿主控制，
   但可以通过保持「全局状态」（任务列表/记忆文件）瘦心来降低每次注入体积。

## 边界

- 以上是 Claude Code 主会话语境的实测结论；Codex 入口层优化见本目录 README。
- token_probe 类对照只验收入口成本；运行期注入是另一个数量级，须分开计量。
- 不为省 token 牺牲监督质量：核验类动作（读码对照、红绿测试）不可省，
  省的是「重复呈现已知状态」的浪费，不是「证据采集」本身。
