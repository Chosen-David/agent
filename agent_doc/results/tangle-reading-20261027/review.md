## Findings from current source

### Declared prerequisites already have a stronger contract than related navigation

`agent_runtime/knowledge.py:KnowledgeStore._validate_links` requires every link target to exist and not self-link; published `requires` targets must be published at the declared version. Its iterative topological check rejects prerequisite cycles. `requires` and `relations` remain distinct fields. A relation may itself have type `prerequisite`, but only the `requires` field participates in enforced closure/version dependencies. A relation label alone does not create the same contract.

`KnowledgeStore.get` returns one isolated entry body and metadata, plus sorted `knowledge_refs` covering the root and transitive `requires` closure. It does not return all prerequisite bodies. `_metadata` computes the same closure for the built-in route without copying body text and deliberately falls back to custom public get hooks.

`KnowledgeStore.context` processes retrieved seeds first, then distinct bounded one-hop neighbors. For each candidate it obtains the entire transitive requires bundle, excludes already selected IDs, and admits every remaining member or skips the candidate. Entry-count rejection occurs before body hydration when already impossible; character-budget rejection occurs after constructing the candidate bundle. It continues to later candidates that may fit. Selected prerequisite bodies receive `selection_reason: prerequisite`; there is no partially admitted declared prerequisite bundle. Before return, nonempty refs go through `check_refs`.

`KnowledgeStore.check_refs` validates exact ID/version/hash, publication and presence of every direct declared prerequisite for every referenced ID. Applying this condition to all refs enforces transitive closure. `check_handoff_knowledge` independently validates consumer-required and producer-supplied bundles, uses the consumer-owned explicit project-relative corpus, and requires producer refs to include consumer-required refs. One side cannot fill the other's missing prerequisites.

Thus no prerequisite-completeness defect is established by a related item being absent. The contract covers declared requires, not all semantically relevant facts or unstated premises. Search/context return applicability unchecked; ref integrity does not certify use of a theorem in a particular scientific setting.

### Bounded navigation and the meaning of ready/partial

`KnowledgeStore.related(kid, limit=20)` accepts only 1..20. It appends outgoing requires first, then outgoing relations, then incoming edges discovered by sorted source ID. It includes only published targets and deduplicates `(type, target_id, direction)`. It returns the first limit results and `truncated = len(results) > limit`. It is one-hop navigation, not semantic ranking or an exhaustive relation closure.

`KnowledgeStore.context(include_related=True)` calls related with the default limit and consumes only its `results`. It does not forward the related `truncated` indicator or enumerate omitted edge IDs/counts. Its `skipped` list describes requested candidate bundles rejected by context entry/character budget. `status` is partial if that list is nonempty, ready if entries exist and it is empty, otherwise no_hits. Consequently ready does not assert that all related edges were examined, nor that search was exhaustive. Optional relations beyond the per-seed cap can be absent without a partial status. Setting include_related=False intentionally removes that expansion altogether.

This is an observable distinction, not evidence of a confirmed functional bug. The docstring expressly describes bounded one-hop navigation; there is no source requirement that every counterexample/application/related edge be mandatory. A possible interface-clarity hypothesis is that callers could mistake ready for relation completeness. Establishing an actual defect would require an applicable caller contract or observed consumer reliance making that interpretation necessary. No such evidence was established in this review. Changing selection, cap or admission priorities would be a behavior change requiring its own scope/plan, not a neutral repair inferred from the paper.

### Correction is explicit dependency invalidation; reconcile is advisory

`agent_runtime/project_memory.py:MemoryLedger._insert` distinguishes candidate from active according to evidence class, validates fixed dependency IDs and current document bindings, and checks noncandidate dependencies. Kinds/evidence/status metadata do not authenticate the natural-language content.

`MemoryLedger._revise` creates a new immutable revision in one write transaction, supersedes the old entry and marks non-superseded declared descendants stale. It prevents reuse of the invalidated lineage as new dependencies. A document-bound correction requires a new current document_refs snapshot. `correct` documents actual user-source responsibility; `accept` only accepts a candidate into a new verified revision. The API checks structural/source text presence, not whether the statement really came from the user or independent verifier. Descendants are not automatically reactivated, and external raw/report files are not rewritten or deleted.

`MemoryLedger._walk`/`check` traverses every declared dependency, rejects any nonactive entry, validates document dependencies, and returns only requested roots for ordinary checks. `_context_closure` retains all validated entries for built-in context hydration in a single read transaction; custom hooks retain fallback semantics. This guards declared dependencies, not hidden semantic links.

`MemoryLedger.list` defaults to active, so candidate/stale/superseded entries are omitted intentionally. `index` is bounded metadata navigation with snapshot-bound continuation and explicit partial/next_after_id, never an acceptance or completeness proof. `history` returns entry plus ordered events, including nonactive history. `impact` returns declared descendants.

`MemoryLedger.reconcile` does not mutate or accept entries. It checks active entries for superseded/stale ancestors, reports newer active siblings in intersecting scopes, and optionally reports multiple user_confirmed active entries in a scope. The last signal counts coexistence, not logical contradiction. It cannot determine natural-language disagreement, resolve intent changes or guarantee all unresolved corrections are surfaced. Native active enumeration and dependency reads share the connection; custom list snapshot consistency is explicitly unchecked. Oversized reconcile output errors rather than silently truncating.

### Declared dissent already survives selected handoff context

`agent_runtime/handoff_basis.py:claim_graph` accepts supported, candidate and rejected claims. Supported claims require declared evidence, satisfied premise records with artifact IDs, and supported parents; records do not prove premise truth.

`check_handoff_basis` validates declared knowledge and memory refs; consumer-required refs must be supplied. Required claims must exist and be supported. `basis_context` optionally narrows context by consumer context_claim_ids, but its included set is selected claims plus required claims plus **all candidate/rejected claims**, then their transitive claim ancestors. It unions their basis with consumer-required refs/artifacts, expands declared knowledge and memory dependencies, and preserves those entries/references. Unselected supported claims may be excluded, with explicit included/excluded IDs. This already protects declared objections and unverified proposals without inventing a new obligation that every related knowledge edge must be loaded.

Known-context hints omit only validated already-held bodies; knowledge refs are rechecked against the hydrated corpus and memory refs checked currently. Their truthfulness as current-context possession remains a host responsibility. Complete serialized payload over character/token budget fails; it does not drop dissent or truncate prerequisites to fit. Artifacts are references, not automatically embedded artifact bodies.

`agent_runtime/communication.py:Mailbox.prepare_context` first consumes/validates the delivered handoff then calls basis_context. `consume_handoff` validates immutable event references and parses the manifest bound to its event hash, rechecks consumer basis and stores immutable record/request binding. ACK is separate. This is stronger than search navigation and should not be conflated with KnowledgeStore.context's partial candidate packing.

The preservation scope is declared candidate/rejected evidence_claims in that handoff. It does not discover a dissent statement absent from the record, a separate ledger candidate, an omitted source paragraph, an undeclared correction, or negative evidence encoded solely as an unselected supported claim. Current source provides no universal must-include schema for all such content. Any proposed broader rule needs an independently established consumer requirement and definition of relevant dissent.
