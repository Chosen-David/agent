# KERNEL-FEEDBACK-01 independent code/data review, initial candidate

Reviewer: host-dispatched `/root/kernel_feedback_review`, independent of implementation author. Scope: actual dirty candidate code and generated standalone references, synthetic CPU log parsing and evidence correctness. No GPU compilation, timing or performance claim is validated.

Decision: request changes. Task preacceptance requires zero semantic errors and no cross-function attribution. Two reproducible defects violate that condition.

1. **P2: resource regexes reinterpret unsupported numeric syntax as a different integer.** In `compiler_feedback.py` METRICS, word boundaries allow matching a numeric suffix. With an otherwise complete supported report, `-12 bytes smem`, `1.5 bytes smem`, and `1,024 bytes smem` become 12, 5, and 24 respectively; `-16 bytes spill stores` becomes 16. All four produce `parse_status=parsed`, no diagnostic/issue and apparently usable metrics. Unsupported/malformed values must stay unknown or be rejected, never silently become a new value. Actual inputs and outputs: `negative_smem`, `fraction_smem`, `comma_smem`, `negative_spill` `.log` / `.json`.
2. **P2: unfamiliar or truncated function headers fail to clear the current function.** The fallback boundary check requires exact `Compiling entry function` spacing/spelling. After kernel `a` header and stack row, `ptxas info : Compiling entry funct` or `ptxas info : Compiling  entry function 'b' for 'sm_90'` yields only an unparsed-info issue; a following `Used 80 registers` is attributed to `a`. `partial` warns about incompleteness but does not make the metric attribution correct. Unknown boundaries must close the old scope conservatively. Actual inputs and outputs: `truncated_new_header` and `whitespace_new_header` `.log` / `.json`.

Nonblocking implementation observation: each metric recomputes previous values by scanning every observation. On this environment, 1,000 repeated rows took 0.016s and 4,000 took 0.229s, consistent with the inspected quadratic scan; these are parser CPU observations, not GPU results or reliable benchmarking. The input is capped at 8 MiB, but observations are not separately capped. A running set per metric would avoid this without changing evidence semantics.

Independent checks used `adversarial_review.py`, not the author tests as oracle. `adversarial-results.json` binds original parser SHA256 `3320d6b3e3c0cccba65fe14b2a33ec098c696bd69299ffcaac641650d3cadf38`, reports the six failing adversarial cases and three passing control cases, verifies log hashes, and records a standalone CLI/API equivalence check. The copied main-role parser is byte-identical. Package-local reference links resolve within both standalone packages, recorded in `source-binding-initial.json`. Author unit tests were run only as supplementary evidence (`author-tests-initial.txt`), not as independent correctness proof.
