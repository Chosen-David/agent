## Design assessment

The proposed capability rename must precede every move of an existing target; the existing final old-copy snapshot check still precedes that move. The new candidate then publishes from private `ready` with the same native helper. On publication refusal or failure, rollback must use that helper as well. When rollback cannot restore the old copy, stage retention and SkillCopyRecoveryError(ValueError) are the declared outcome, including recovery_path and both original and rollback errors. Normal success and uncontended rollback clean their owned stages. This is internally consistent with the scoped preservation property and CLI's existing controlled exit2 boundary.

Reusing the private ingestion helper creates cross-domain coupling and imports its module dependencies into setup. That is a real maintenance tradeoff, but not material enough to block this repair: the implementation is already dependency-free within this checkout, the exception is compatible, and no standalone Skill export or ingestion ABI must change. The helper's ingestion-specific diagnostic text is imperfect but truthful about unavailable publication. A broad shared-module extraction is reasonably deferred.

The existing portable failure fixture currently hooks Path.rename only for `new`→exact skill target. Without alignment it would silently stop injecting the failure after this repair. The plan explicitly aligns it to the actual helper boundary and `ready` name, while keeping assertions. This alignment must be frozen before baseline alongside the new tests, so the before/after comparison measures the same failure condition rather than a weakened regression.
