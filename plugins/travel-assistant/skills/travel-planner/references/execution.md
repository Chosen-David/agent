# 执行与验收补充

这些步骤细化已有职责；不改变用户目标、权限或外部 API。按本次任务需要应用，不要求简单问答生成全套文件。

1. 将本地 RequestContract/DeliveryBundle 视为行为记录，绝不能直接发给 JourneyPilot 的同名 API。复杂任务至少维护：约束与修订号、候选事实及来源、允许的候选选择、行程、通勤、预算、未知项、交付版本；研究角色只返回候选，主规划负责选择和验收。

2. 逐项准入后再排时间：精确分店/地址；service_windows 为多个独立区间；完整活动时长加最后点单/入场约束；转场含步行候车、缓冲；午休为独立块。必须活动若未知/冲突就保留明确缺口，不能悄悄换店或删掉。

3. 费用按 共享契约的 per_person/per_package/per_car/per_room/total（输入 per_group/per_vehicle 显式映射为 per_package/per_car 并保留原单位） 区分。按人数/车辆/间夜计算，再合计预算和机动金；未知价格不能当零。改交通后重算后续时间，改变约束只失效相关候选/路线/输出。新文档和聊天引用同一修订号。

4. 先查无需登录的公开来源；不足时分开标候选与已核验。缺档期不能写已预约。中断后复用仍有效证据，不重跑全量查询。当前补充完善本地执行验收，字段以 planning_contract.md 的 local-travel/v1 为准；不另造第二套字段权威，不实施外部 runtime 迁移。

复杂交接附实际输入版本、产物路径、已执行检查、限制与下一负责人。外部后端发现不等于可运行或已授权；没有后端时用当前工具完成有界任务。

知识需求与交接按 [知识接入契约](knowledge_access_workflow.md) 执行；保留实际查询/前提核对证据及完整 knowledge_refs，无需求时注明原因。
