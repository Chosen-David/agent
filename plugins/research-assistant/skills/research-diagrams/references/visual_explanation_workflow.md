# 网页会话中的图解教学

供 `explain-research-concepts` 发起、`research-figures` 协调及图形专业角色消费。用于帮助用户理解当前问题，不把一次问答扩成论文配图工程或网站建设。本文件是可移植执行规范，不提供模型调度、渲染器、附件通道或安装服务。

## 1. 先决定图能帮什么

先用一两句话回答，再根据当前误解选择表达方式。用户要图，或过程、几何、依赖、对比/参数变化难以用短文字解释时，主动调用作图能力；一句定义/简单代数足够，或用户只要文字时直接解释，不为了“生动”强制派发。

- 机制、张量流、状态转移、几何关系：`diagram` → `research-diagrams`。
- 公式的准确曲线、分布、数值对比：`data_visualization` → `research-data-visualization`，标明 theoretical 或 synthetic，不能当实验结果。
- 同一教学图同时需要结构和数值：`mixed` → `research-figures` 负责整合；纯图只走一个专业角色。
- 类比插画仅辅助直觉，说明它在哪失效；数学、拓扑和数据必须有精确图源/验算，不能让生图模型猜数字、连线或公式。

`explain-research-concepts` 是最终讲解 owner。已提供独立 Agent/技能调用接口时，实际派发教学 brief 给 `research-figures` 或其已确定的专业角色，并读取返回产物；不要只建议用户再去找作图 Agent。若当前角色不能派发，把 brief 交回主 AI 由其调用。已直接分配专业角色的任务不额外绕回协调层。

没有子 Agent、对应技能或调度接口时，由同一模型按本文件顺序完成必要的作图与讲解，记录 `sequential_fallback`；不能把角色名写进回答就声称已调用另一位 Agent。发现权限不足仍遵守宿主批准规则，角色交接不增加权限。

## 2. 从直觉到精确，保持图文对齐

按问题选最小的教学序列，通常从一个可手算例子开始，需要时才增加面板：

1. **直觉**：先画对象、目标和目前已知的信息，只突出一个关键关系。
2. **过程**：在同一个例子上逐步加入操作，明确每步保持什么、改变什么。用局部高亮或少量面板，不把所有中间量塞进总览。
3. **精确与边界**：将图中对象对应到公式/代码变量，再用一个边界情况或反例限制类比。已有基础的用户可以直接从这步开始。

使用稳定的 `EXPL-*`、`S1/S2`（讲解步）与 `P1/P2`（面板）标识；这是内部自动维护的轻量引用，不要求为简单问答建立文件体系，不让网页用户填写任务 ID、manifest 或配置环境。每个面板对应明确问题和讲解句；同一个符号、颜色、形状跨面板保持同一含义，必要时同时用文字/线型区分。箭头注明“数据流/操作/依赖”等含义，不用同一种未解释箭头混表示因果与相关。

解释顺序跟随图中编号。caption 说明如何读，alt text 用不依赖看图的短句表达同一个机制。若用户继续追问，只修改相关步和依赖面板；改了数值、符号或前提，图、caption 和解释一起更新，重验受影响部分。

## 3. 最小双向交接

普通问答把下面内容合成一段 brief 即可；复杂/多轮任务才保存结构化记录。优先复用已有 figure notes / handoff，别另造调度系统。

解释方交给作图方：

- 当前问题、用户基础/语言、要解除的具体误解、解释 ID 和输入版本。
- 已核实的定义/公式、符号及形状/单位、一个小例子、原文锚点/来源或“无论文，只讲一般机制”。保留适用的 knowledge_refs 与前提核对，不能用类比偷偷替换模型。
- 每步 `step_id → panel_id → 要看见的变化/必须保持的关系`；需要哪种 route。没有必要拆分时只保留一组。
- 网页会话目标、预计显示宽度、所需预览/可编辑源、已查明的渲染/附件/交互能力，以及允许写入位置和当前授权边界。

作图方返回解释方：

- 同一解释 ID、输入版本、step/panel 映射与 route；实际生成文件及可编辑主源，复杂交接附哈希/复现步骤。
- caption、alt text、符号/颜色/箭头映射；标清 schematic / theoretical / synthetic / measured。
- 独立列出语义/数值与视觉检查的结果、实际检查产物/尺寸和具体观察；未知、失败、未执行分别记录。
- 缺口与下一负责人。修订保持原发现 ID，不能用“完成渲染”替代解释方消费验收。

解释方实际读取图与结果，逐项核对原问题、输入版本、步序和术语，再组织短答案 + 对应图 + 必要精确说明；不要把未经检查的图直接转发。若独立 reviewer 可用且任务复杂，让其先对照原材料审查，不能把生产者自评当独立验收。

完整仓库的复杂文件交接可复用 `scripts/validate_handoff.py` 和消费者独立持有的 `templates/handoff_request.json`，从已授权教学步骤确定 tasks，执行 `--require-complete --request`。只安装单个 Skill 或无脚本时用同一范围/版本/产物检查手工交接。哈希与任务完整性通过不证明科学或视觉正确；不为一次小问答强制生成 manifest 或启用持久收件箱。

## 4. 两道检查，失败后只修相应部分

**语义/数值检查**：解释方或审查者对照真实输入核查节点、箭头、操作顺序、形状/单位、关键数值、归一化与边界条件；同一个教学例子在图和公式里要一致。可计算项实际复算；数值例子不是一般证明。未知原文结构不能自行补齐，示意和测量不能混标。

**视觉检查**：作图方实际渲染并打开最终输出，再在预计会话宽度查看。未指定时可用约 720 px 的预览宽度作为可调整初值，明确这是教学显示假设而非平台规格。检查标签可读、无裁切/遮挡、箭头终点清楚、顺序明确、颜色有冗余编码；中文/数学字符不能缺字。面板合并或缩放后必须再查看整图。

语义通过但字体挤：拆面板/减标签，不改机制。视觉漂亮但机制错：先修关系/数值再渲染。任一未通过保留 draft，具体反馈给作图方；按现有任务预算修正，通常两次返修仍不清楚就重新诊断布局或说明阻塞，不通过不能称已验收。

程序可帮助发现文件缺失、算错或版本不匹配，不能证明图已经被看过。语义 pass、视觉 pass、文件已发送、用户已看到是四种不同证据。

## 5. 网页会话交付与能力降级

执行前从当前工具列表/结果确认渲染、图片查看、上传/原生附件和交互显示能力。网页聊天本身不证明这些能力存在，也不要求连接用户电脑。遵循当前宿主的消息格式与文件交付规则，不照抄别的平台调用名或参数。

1. **有渲染 + 文件交付**：在云端或已授权环境生成图，保留 SVG/绘图代码等可编辑源，以宿主支持的 PNG 等预览交付。若有 Library 上传和原生附件通道，先上传实际文件、取得真实文件 ID，再按当前消息工具 schema 附上它。上传成功不等于发送成功，发送受理也不等于用户已经看过。
2. **有实际内嵌交互组件**：只有改变参数确实帮助理解时才用；提供初始值、范围、单位、固定对照和静态替代，实际检查控件与计算一致。不为“网页版”默认创建/发布网站。HTML 源或附件不是已经内嵌运行的交互界面。
3. **可生成但不能实际查看**：标记视觉未检查，不能称图已通过；先给足以独立理解的文字。仅当用户要草稿时交付并明确草稿状态，保留可继续检查的文件。
4. **可生成/检查但没有附件通道**：直接解释当前问题，说明该图尚未在会话中交付；保留文件供支持的通道后续使用。不要把本地路径、私有下载地址或桌面专用链接当网页可打开的附件。
5. **没有渲染能力**：用短分步文字和手算例子完成能解释的部分。若用户明确要图，说明缺的是生成/显示能力；可提供图稿描述，但不能把 Mermaid/SVG 代码或“想象一张图”冒充已渲染图片。只有确认客户端能显示该格式时才使用它。

图片旁只放当前问题的关键解释、面板对应和适用边界；别向用户倾倒内部 brief、QA 清单或执行报告。用户请求源码/详细推导时再给。内容修订后发新版本并说明变化，发送结果不确定先查证，避免重复发送。

仓库修改、插件打包、目标宿主安装及本次会话实际调用分别验证。仅更新仓库或 Claude Code setup 不会自动更新 ChatGPT 网页已安装的同名个人 Skill；没有目标安装与运行证据时，只报告仓库能力已准备好。
